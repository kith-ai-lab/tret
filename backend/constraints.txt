# Pins every dependency pip resolves for `pip install -e ".[dev]"` — direct and
# transitive alike — to the exact versions this repo is tested against, so CI
# installs the same thing today and next year instead of "whatever satisfies
# the >= ranges in pyproject.toml right now."
#
# This is deliberately NOT a lockfile tool (uv, pip-tools, Poetry): pyproject.toml
# stays the single source of *what* tret depends on and stays installable the
# ordinary way for a contributor who just wants `pip install -e ".[dev]"` to work
# without learning a new tool. This file only narrows the *versions* pip is
# allowed to pick, via pip's own `-c`/`--constraint` flag — no new tooling, no new
# concept, one file:
#
#   pip install -e ".[dev]" -c constraints.txt
#
# A constraint never adds a dependency that pyproject.toml did not already ask
# for; it only pins the version of one pip would otherwise have installed. If
# pyproject.toml grows a new dependency, pip will still install it (unpinned)
# rather than erroring — the two files are complementary, not required to be
# perfectly in sync, though re-freezing after a dependency change is good
# practice.
#
# Regenerate after intentionally upgrading a dependency, from a clean install:
#
#   cd backend && rm -rf .venv && python3.12 -m venv .venv \
#     && .venv/bin/pip install -e ".[dev]" \
#     && .venv/bin/pip freeze | grep -v '^-e ' > constraints.txt
#
# The `grep -v '^-e '` drops the editable self-install line pip freeze emits for
# `tret` itself (a `file://` or `git+ssh://` reference to this checkout) — that
# line describes the environment freeze was run in, not a dependency, and is
# actively wrong to pin (it would freeze CI to installing over ssh from whoever
# generated it).
